# 組織以成員資格掛在全站帳號上，貼文以可升降的 audience_tier 控制可見範圍

組織（學校、企業、機構）的淘汰物品要分層釋出：先給內部單位（`internal`），沒人要再給組織成員（`members`），最後公開（`public`）。因為同一件物品會從組織內部流到公開平台，同一個人（例如學生）也同時是組織成員與公開平台使用者，所以我們**不做租戶隔離**，而是：

- **帳號全站唯一**。組織身分存在 `org_memberships`，用另外驗證的 `org_email` 取得，與登入 email 分開。學生畢業失去學校信箱時，帳號和交換紀錄仍在。
- **「看得到什麼」與「能管什麼」是兩個欄位**：`access_level`（`internal`／`member`）決定可見範圍，`org_role`（`admin`／`member`）決定管理權限。
- **Unit Contact 不是 `org_role`，而是單位指派（`org_unit_contacts`），與 Org Admin 互相獨立（2026-11-08）**：一人可以同時是 Org Admin 與幾個單位的窗口，例如兼任總務處窗口的總務主任。`access_level` 由這兩者在寫入時推導：Org Admin 或 Unit Contact → `internal`，其餘 → `member`。原本 `org_role` 有 `staff` 值代表窗口，三選一的設計讓「管理員兼窗口」無法表示。組織至少要留一位 Org Admin，移除或降級最後一位會被擋下。
- **Platform Admin 可進入任何組織的組織後台（2026-11-08）**：開通後的營運支援（補加管理員、修正成員）不必先把自己加為該組織成員，避免為了支援而在組織裡留下多餘的 membership。Platform Admin 不因此取得看 Internal／Members 物品的權限：可見範圍仍只來自 membership。後台以外，不是該組織 Org Admin 的人一律得到 404 `ORG_NOT_FOUND`。
- **貼文帶 `org_id`、`org_unit_id`、`audience_tier`**。`org_id IS NULL` 就是一般個人貼文，等同 `public`，現有資料不受影響。物品屬於單位，不屬於上架的個人，承辦人離職時紀錄不會斷。
- **可見範圍可以疊加**：每個請求先算出使用者的範圍清單（例如 `public`、`org:12:internal`、`org:12:members`），MySQL 與向量索引的 `scope` TAG 都用同一份清單過濾。因此不需要「切換組織」。向量索引 `idx:posts_v` 的每份文件都帶 `scope`（個人貼文與 Public 層為 `public`，其他為 `org:<id>:<tier>`），層級改變時要同步更新它；KNN 在取 K 筆之前就以 `scope` 預先過濾，而不是取完再丟，否則 K 筆候選可能大半是看不到的貼文。MySQL 端的條件仍保留，作為第二道防線。
- **Prototype 版的例外（2026-11-07）**：疊加只套用在 `public`。Internal／Members 物品**只在獨立的組織頁顯示**，現有 Feed、搜尋、熱門排行、向量推薦一律排除 `audience_tier <> 'public'` 的組織貼文；組織頁上方有切換器，一次看一個組織。原因：完整疊加要讓約 39 處讀取 `posts` 的 SQL 與向量索引各自判斷使用者能看哪些層，漏一處就洩漏內部物品；「排除非公開組織貼文」只是一條條件，漏掉時頂多是看不到。Prototype 要驗證的是三層流程，不是混合 Feed。完整疊加與「是否還需要切換組織」待試點後再決定。
- **演示組織可跳過待公開期**：平台管理員可把組織標為演示組織（`is_demo`），只有這類組織的管理員能跳過 10 分鐘待公開期，方便演示。一般組織不能跳過，因為待公開期是公開前的主要防線（見下節）；把跳過綁在組織上，而不是所有管理員或環境變數，是為了讓 prototype 直接上正式環境時，真實客戶的組織仍受保護。
- **能認領 = 能看到**，同一條規則。看不到的貼文回 404，不回 403，不洩漏物品存在。

## 層級可升可降

降級是為了補救誤公開。只要沒有 `approved`／`completed` 的 Weave 就可以降級；不符合新層級的 `requested` 請求自動改為 `declined` 並通知對方。升級到 `public` 先進入 10 分鐘的待公開期，這段期間不進排行、不發通知，可一鍵取消。

降級無法收回已被 LINE／Facebook 抓取的分享預覽、已送出的通知與私訊、截圖。所以延遲生效才是主要防線，降級是第二道。

## Considered Options

- **每個組織一個獨立租戶（`tenant_id` 硬隔離、每租戶各自帳號）**：隔離最乾淨，但物品無法跨層流到公開平台，學生在學校與公開平台會是兩個帳號，和分層釋出的需求衝突。
- **每個組織獨立部署**：維運成本隨客戶數線性成長，不適合學校這種客戶多、單價低的市場。
- **層級只升不降**：邏輯較簡單，但操作錯誤時無法補救。
- **成員身分只有一個 `role` 欄位**：例如總務承辦同時需要「看內部物品」和「管理組織」，單一欄位會讓這兩件事綁在一起。

## Consequences

- 所有讀取 `posts` 的路徑（Feed、搜尋、詳情、留言、按讚、Weave、Socket、SEO metadata）都必須經過同一個可見性 helper，漏掉任何一處就會洩漏內部物品。需要專門的隔離測試覆蓋。
- 公開熱門排行 `feed:trending` 只收 `public`；組織內清單量小，直接查 MySQL。
- 私訊維持全站共用，不受組織限制，只檢查和貼文相關的內容：附帶貼文資訊時，寄件人與收件人都要看得到該貼文，否則回 404，避免 Internal 成員把內部物品的資訊私訊給組織外的人。
- 若未來有客戶要求資料實體分離，需要另外設計，本決策不涵蓋。
