# 組織物品的 Weave 記錄「代表哪個單位」，對外以組織名義顯示但由窗口個人帳號接收

組織物品的擁有者是單位，不是個人（ADR 0003）。因此 Weave 沿用 ADR 0001 的物品流向模型，但多一欄 `receiver_org_unit_id`：`receiver_id` 是經手的個人，`receiver_org_unit_id` 是物品實際流向的單位，與貼文的 `user_id`（經手人）／`org_unit_id`（擁有者）對稱。若這欄改由 membership 推導，窗口離職或調單位後，流轉紀錄（PRD E9）會在事後改變。

`receiver_org_unit_id` 由申請人在送出請求時選擇，不由層級推導。Unit Contact 是單位指派，與 Org Admin／Org Member 身分互相獨立（ADR 0003），所以一個人可能同時代表好幾個單位、又能以個人身分交換：同時具有 Unit Contact 與 Org Member 身分（或是多個單位的窗口）的人，申請時選「代表某單位」或「我個人」；只有一種身分的人不會看到這個選項。例如業務部的螢幕 30 天沒人要、已升到 Members 層，工程部才臨時需要，窗口仍要能以單位名義申請，否則有財產編號的資產會被記成員工個人帶走。

公開層的發文者對外顯示依組織設定（組織名稱、組織＋單位，或匿名），但 Weave 對話與私訊仍是現有的一對一模型，由經手窗口的個人帳號接收；其他窗口或組織管理員接手時，把對話的 `user_id` 轉給新窗口。我們沒有做單位共用收件匣，因為那要改造整套 Messages 與 Socket 的一對一模型；也沒有直接顯示窗口本人，因為會曝光員工個人帳號，並讓組織的匿名設定失去意義。

## Consequences

- 所有顯示發文者的地方（貼文卡片、詳情頁、Weave 對話、通知、SEO metadata）對組織貼文都要改用組織顯示名稱，漏掉一處就會曝光窗口本人。
- 一般個人 Weave 的 `receiver_org_unit_id` 為 NULL，行為不變。

## 組織對話與聯絡代號（2026-11-12，#140）

- **組織物品的對話與兩人的個人對話分開**：`conversations` 多 `org_id`／`org_user_id`，唯一鍵是 (兩人, 組織)。原本一對帳號只有一個對話，民眾若另外用窗口的個人帳號私訊，會落到同一個對話，等於揭露窗口是誰。
- **聯絡代號取代窗口的 `users.public_id`**：公開介面給 client 的發文者是 `org-post:<貼文 public_id>`，server 解析成目前的經手窗口（`posts.user_id`，交接後自動換人）；組織對話裡的對方是 `org-conv:<對話 id>`，兩邊回訊息都留在同一個對話。窗口的名稱、頭像、email、數字 user_id 都不出現在公開介面。
- **誰看到組織名義**：公開介面（Feed、搜尋、詳情、SEO、個人頁）對所有人遮蔽，只有窗口本人看自己的物品時不遮；兩人之間的畫面（Weave、通知、私訊、留言回覆通知）只對不是該組織成員的人遮蔽，同組織的同事照舊看到彼此。對話沒有單位脈絡，「組織＋單位」設定在對話裡只顯示組織名稱。
- 交接（#142）改為把 Weave 指向新窗口與申請人的組織對話，民眾看到的仍是組織名義。
