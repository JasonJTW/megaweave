# PRD：組織分層釋出（Org Tiered Exchange）

- 狀態：Draft
- 日期：2026-10-28（2026-10-29 更新：新增 E9 物品流轉紀錄、財產合規待確認問題）
- 相關：技術差異分析見 `docs/design/0001-org-tiered-exchange-gap-analysis.md`

## 1. 背景與問題

學校、企業、機構定期有淘汰物品（電腦、桌椅、廚具、實驗設備）。目前常見做法是公文／Email 詢問各單位，或請工讀生在公開平台發文。問題：

- 組織內部各部門資源不透明，A 單位閒置的東西，B 單位不知道
- 好東西一公開就被外人拿走，另一個單位隔月又要採購新的（重複採購）
- 有財產編號的物品不能直接送人，要先走移撥或報廢程序
- 總務要跑各單位收集「有什麼要丟」，最花人力的是這一步
- 只有零散貼文，沒有可放進永續報告／評鑑的統計
- 畢業季、實驗室搬遷等大批量時人力撐不住
- 承辦人員異動後流程和紀錄斷掉

**比較基準（最強替代方案）**：請工讀生在現有平台用公開帳號發文。本產品只有在解決上述「工讀生方案做不到」的問題時才有價值。

## 2. 目標 / 非目標

**目標**
- G1 組織內部優先流通，降低重複採購
- G2 讓各單位自助上架，降低總務行政人力
- G3 產出可稽核的減廢／減碳數據
- G4 內部沒人要的物品，可順暢釋出到公開平台（大量交織／地球公物）

**非目標（本期不做）**
- 獨立網址／子網域、客製品牌
- 計費與方案管理
- 與學校財產管理系統串接（第一版以手動填寫財產編號＋CSV 匯入匯出銜接）
- 取代學校既有的財產管理系統（本產品只記錄「準備釋出」的物品，是財產系統的釋出前端）
- 可交易碳權（避免排放量僅作報告數據，不作抵換）

## 3. 使用者角色

| 角色 | 說明 |
|---|---|
| 平台管理員 | 我們。開通組織、全站管理 |
| 組織管理員 | 例：總務處承辦。可多位，管理成員、單位、釋出、報表 |
| 單位窗口 | 例：各處室職員。代表單位上架物品、認領物品 |
| 組織成員 | 例：學生、一般員工。第二層開放時可認領 |
| 公開使用者 | 現有平台使用者。第三層開放時可認領 |

## 4. 分層定義

| 層級 | 可見／可認領對象 |
|---|---|
| Tier 1 內部單位 | 該組織的單位窗口（職員） |
| Tier 2 組織成員 | Tier 1 ＋ 該組織所有驗證成員（如學生） |
| Tier 3 公開 | 所有人（現有平台） |

物品可以升級，也可以降級（用來補救誤操作）。只要還沒有已核准的 Weave，就可以降級；降級後不符合資格者的待審請求會自動婉拒。

## 4.1 Item Lifecycle（物品生命週期）

一件物品從被列為可釋出到交接完成的完整流程。括號內為對應的 Epic。

**開始之前（一次性設定）**
- 平台開通組織，設定允許的信箱網域（E1）
- 組織設定多位管理員、各單位與窗口（E1）
- 職員與學生用組織信箱驗證後加入組織（E1）

**1. 列為可釋出、上架**
- 單位窗口代表單位上架，物品屬於單位、不屬於個人（E3）
- 填寫物品資訊與照片；財產編號選填；可填估算重量與價值（E4、E6）
- 或由總務匯入財產系統的「待報廢清單」批次上架（E7）
- 上架後預設在 Tier 1（E2）

**2. Tier 1：內部單位**
- 只有組織職員看得到、能申請（E2、E5）
- 管理員在後台看全組織待釋出清單，可依單位、層級、狀態篩選（E3）
- 其他單位申請，物品單位核可後交接；記錄單位間移轉（E9）

**3. 開放到 Tier 2：組織成員**
- 管理員手動開放，或設定 N 天無人申請自動開放（E2）
- 學生也看得到、能申請；可限制每人申請數量（E5）

**4. 開放到 Tier 3：公開**
- 有財產編號者，需管理員先確認已完成報廢等程序（E4）
- 確認視窗列出物品名稱與財產編號，確認後有 10 分鐘緩衝可取消（E2）
- 正式公開後，所有平台使用者可見，進入搜尋與熱門排行

**5. 誤公開補救**
- 沒有已核可的申請前可降級；不符資格者的待審申請自動婉拒並通知（E2）
- 從公開搜尋與排行中移除

**6. 交接完成**
- 物品單位核可申請，雙方確認交接後完成（沿用現有 Weave 流程）

**7. 紀錄與報表**
- 每件物品從上架、層級變更、申請到交接完成皆有時間軸（E9）
- 匯出流轉紀錄，供總務回財產系統補登移撥或報廢（E9）
- 統計去化率、流通件數、估算重量與減碳量，可匯出（E6）

**8. 人員異動**
- 窗口離職時，物品與進行中的申請可轉交新窗口（E8）
- 所有管理操作留有紀錄（E8）

## 5. 需求（Epic → User Story → 驗收條件）

優先度：**M** = 試點必須、**S** = 應該有、**C** = 之後再做

### E1 組織與成員

| ID | User Story | 優先 |
|---|---|---|
| E1-1 | 身為平台管理員，我想建立組織並設定允許的 email 網域，以便該組織成員可以加入 | M |
| E1-2 | 身為使用者，我想用組織 email 驗證身分加入組織，以便看到內部物品 | M |
| E1-3 | 身為組織管理員，我想設定多位管理員，以便分工與交接 | M |
| E1-4 | 身為組織管理員，我想建立單位並指定單位窗口，以便各單位自行上架 | M |
| E1-5 | 身為組織管理員，我想區分職員和學生（網域或名單），以便控制 Tier 1／Tier 2 | M |
| E1-6 | 身為組織管理員，我想停權成員 | S |

驗收條件（E1-2）：
- Given 組織允許網域 `school.edu.tw`，When 使用者輸入 `a@school.edu.tw` 並點擊驗證信連結，Then 成為該組織成員
- Given 使用者輸入 `a@gmail.com`，Then 無法加入並顯示網域不符
- Given 未點驗證信，Then 不具成員身分

### E2 分層釋出（對應：內部優先）

| ID | User Story | 優先 |
|---|---|---|
| E2-1 | 身為單位窗口，我想上架物品時預設在 Tier 1，以便內部優先 | M |
| E2-2 | 身為組織管理員，我想手動將物品升級到下一層 | M |
| E2-3 | 身為組織管理員，我想設定「N 天無人認領自動升級」 | S |
| E2-6 | 身為組織管理員，我想把誤公開的物品降回較低層級，以便補救操作錯誤 | M |
| E2-7 | 身為組織管理員，我想讓升級到 Tier 3 延遲 10 分鐘生效，期間可一鍵取消，以便在公開前發現錯誤 | M |
| E2-4 | 身為使用者，我想看到物品目前在哪一層、何時可能釋出 | S |
| E2-5 | 物品升級時，新一層的對象收到通知 | C |

驗收條件（E2-2）：
- Given 物品在 Tier 1，Then 學生與公開使用者在 Feed、搜尋、詳情頁、分享連結都看不到
- When 升級到 Tier 3，Then 公開 Feed 與搜尋可見
- 升級紀錄（誰、何時、從哪層到哪層）可查

驗收條件（E2-6）：
- Given 物品在 Tier 3 且沒有已核准的 Weave，When 管理員降到 Tier 1，Then 公開使用者在 Feed、搜尋、詳情頁都看不到（詳情頁回 404）
- Given 有公開使用者的待審 Weave 請求，When 降級，Then 該請求自動婉拒並通知對方
- Given 已有核准或完成的 Weave，Then 不能降級
- 降級紀錄與升級紀錄一起保存

驗收條件（E2-7）：
- When 管理員將物品升級到 Tier 3，Then 先顯示確認視窗（列出物品名稱與財產編號），確認後進入「待公開」
- Given 物品在「待公開」，Then 仍依原層級顯示，不進公開排行、不發通知
- When 10 分鐘內按取消，Then 維持原層級，並留下紀錄
- When 10 分鐘到，Then 正式升級到 Tier 3

### E9 物品流轉紀錄（對應：資源不透明、財產合規、人員異動）

記錄每件「準備釋出」的物品從上架到交接完成的完整過程。不取代學校的財產管理系統，而是讓總務能據此回到財產系統補登。

| ID | User Story | 優先 |
|---|---|---|
| E9-1 | 身為組織管理員，我想查看每件物品的流轉時間軸：上架單位、財產編號、層級變更（誰、何時）、申請、核可、交接完成、領取單位或個人 | M |
| E9-2 | 身為組織管理員，我想依期間、單位匯出流轉紀錄 CSV，以便回財產管理系統補登移撥或報廢 | S |
| E9-3 | 身為組織管理員，我想看到全組織閒置物品清單與去向，以便掌握各單位資源 | M |

驗收條件（E9-1）：
- Given 物品已完成交接，Then 時間軸顯示從上架到完成的每一步，包含操作者與時間
- Given 單位窗口已異動，Then 歷史紀錄仍保留原操作者，物品歸屬維持在單位
- 紀錄不可被一般成員修改或刪除


## 6. 成功指標

- 試點期間 Tier 1 去化率（內部認領件數 ÷ 上架件數）
- 經 Tier 3 釋出到公開平台的件數
- 組織管理員每月處理時間（訪談）
- 試點組織是否願意付費續用

## 7. 待確認問題

1. 「沒有需求」的判定：自動（N 天）或手動？
2. 職員與學生如何區分：不同網域或名單匯入？
3. Tier 1 單位間認領是否需要主管核准？
4. 註冊：網域符合即通過，或需管理員審核？
5. 財產處分合規（需學校總務／財產管理單位確認）：
   - 「財產」（一般為價值 1 萬元以上、使用年限 2 年以上）與「物品」如何區分？哪些可以釋出？
   - 校內單位間移轉要填什麼單、誰核准？流轉紀錄需要哪些欄位才能直接使用？
   - 財產能否給學生個人（Tier 2）？國有動產贈與的受贈對象不含個人，是否只有物品或已報廢者可給？
   - 已報廢物品能否免費公開給社會（Tier 3），還是只能變賣或清運？
   - 未達使用年限的財產能否釋出？
   - 資訊設備釋出前由誰清除資料、是否要留紀錄？
   - 實驗室設備（化學、生物、輻射疑慮）是否禁止釋出？
   - 第一個客戶是公立學校、私立學校還是企業？（規定與稅務處理不同）
6. 組織物品是否開放 ECPay 付款與 Lalamove 配送？

## 8. 試點前的零開發驗證（Phase 0）

在開發前，先用現有平台幫一所學校人工跑一輪釋出（例如期末清空），觀察：內部是否搶著要、是否卡在財產程序、是否有人要報表。依結果調整本文件的優先度。
